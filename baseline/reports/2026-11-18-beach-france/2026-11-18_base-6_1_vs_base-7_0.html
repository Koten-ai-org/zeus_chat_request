Better, worse, and the score

The verdict column compares base-7.0 with base-6.1 on the Target API column. It does not score which prose answer was nicer. A different verb that still returns rows is not a hit.

  • better: base-7.0 called the target API and base-6.1 did not.
  • worse: base-6.1 called the target API and base-7.0 did not. On “Find hoppy citrus beers” the target is search hybrid. That row is worse when base-6.1 calls search hybrid and base-7.0 calls search fts, find, or set, even when both sides are HTTP 200 and both returned beers.
  • both hit: both packs met the target.
  • both missed: neither pack met the target.
  • not run: a model call is missing, so the row is left out of the score.
  • Orange: a pack cell ends on HTTP 400 or higher, so the row is re-tested later. The source is LLM when the model sent a request Zeus rejected, Zeus when the service closed or failed the call, and koten_converter (FUTURE) when that hop reports the error. koten_converter is not wired into this suite yet. Orange stays out of better and worse. An earlier HTTP 400 on a turn that ends at 200 stays in the HTTP chart and does not turn the row Orange.

Both hit and both missed stay out of the better and worse counts. The score still counts them as same. When the question says rows are required, an empty Zeus result is not met. In a pack cell, pipeline means a pipeline ran. fts means the target was hybrid and this side called fts instead.
